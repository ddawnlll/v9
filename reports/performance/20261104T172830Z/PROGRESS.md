# BTC development-window measurements — INCOMPLETE

The architecture monograph explicitly identifies BTCUSDT 1h, 2025-01-01 through 2025-04-01 as development data. Its individual January–March archives were copied to an isolated directory; SHA-256 hashes match the accompanying vendor checksum files and are in environment.json. No combined four-year tape or sealed OOS data was read for these measurements. Earlier notes claiming no historical tape was found were wrong: the configured sibling V8 data root contained it.

Three fresh-process runs of the actual `BenchmarkRunner` including its ledger, result JSON and verified forensic HTML took 1.643, 0.819, 0.724 s for January (744 bars) and 1.992, 1.993, 1.956 s for January–March (2160 bars). Peak child RSS ranges were 230.5–246.3 MiB for January and 244.0–245.6 MiB for the three-month case. The first January run followed container start and includes colder caches; subsequent runs had warm caches. Each run completed in an ARM Linux Docker VM with a two-CPU quota and 4 GiB memory limit, hosted on an Apple M3 Pro. This does not predict inexpensive VPS runtime. The runner used its declared `baseline` simulated execution profile, generated zero completed trades, and returned a NO_ECONOMIC_CLAIM certificate; no economic effectiveness is inferred. Gate resolution and determinism reruns were not requested by this harness.

A separate ensemble-only measurement uses the adapter's unspecified default execution profile, not the runner's `baseline` profile, and should not be treated as a matched implementation comparison. Its three-month uninstrumented child times were 1.919, 1.934 and 1.931 s. `timings.csv` partitions one separate instrumented 1.917 s child run: engine.run, inclusive of Python callbacks, occupied 1.620 s (84.5%); loading/input preparation 0.036 s; engine initialization 0.061 s. The interpreter startup, output and teardown are grouped because this harness cannot distinguish them. Parent measurement-file writing and Docker start are excluded. `memory.csv` gives boundary RSS snapshots, not phase-attributed allocations.

The separate cProfile run took 3.260 s, about 69% more than the 1.931 s median uninstrumented run; this is a noisy estimate. It recorded 2160 calls to `on_bar` and 60,480 `observe_expert` calls. Its cumulative times overlap: `on_bar` 2.902 s and `observe_all_28` 2.149 s, plus the latter's nested Polars and indicator work; do not sum these or infer native CPU from the difference. `q1-profile-top.txt` is a text profile, and the binary profile is temporary at `/tmp/v9-real-dev/q1.pstats`. `q1-expert.json` contains inclusive per-expert samples and percentile estimates, separately instrumented; shared lazily initialized feature work is charged to whichever expert first requests it, so the expert ranking is not independent attribution. Exclusive expert timing remains unavailable.

B0 and B1 are measured only for the defined development windows and this machine. `benchmark_matrix.csv` explicitly marks B2–B5 NOT_RUN: they extend outside the explicitly established BTC development window and/or demand unavailable 15m/1m and 40-instrument support. Their data and sealed OOS boundaries have not been authorized or verified. This is not a complete report, not an under-10-second verdict for the target VPS, and not grounds to replace the engine. Goose parity and speed on this actual feature workload, allocation profiling, multi-asset real data and complete stage coverage remain outstanding. `LATEST.md` is intentionally not advanced to this incomplete note.
