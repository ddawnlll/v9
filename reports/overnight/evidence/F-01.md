# F-01 — Durable GitHub-issue queue, lease and crash recovery (#35)

Status: **IMPLEMENTED_WITH_EVIDENCE** (integration and final issue closure remain the director's call).

## Objective

Give the unattended coordinator a bounded, crash-safe bookkeeping plane: claim one eligible
issue, persist ownership and lease, recover ownership after a restart, and stop retrying once
the per-issue budget is spent. The coordinator stores only leases, queues, budgets, status and
telemetry; it never calls GitHub and never decides that an issue is done.

## Storage decision (justification)

**SQLite in WAL mode with `BEGIN IMMEDIATE`, `synchronous=FULL`, `busy_timeout=5000ms`.**
`sqlite3` is in CPython, so this adds no runtime dependency. The claim is a compare-and-swap
(`UPDATE … WHERE state = 'PENDING' AND attempts = ?`), and the lease row + issue row + attempt
counter are written in one transaction, which is exactly the crash property required. A JSON
file with `fcntl` flock would still need torn-write handling, fsync ordering, and atomic
multi-record updates (issue state + attempt count + lease audit row); reimplementing that is a
larger failure surface than the embedded database the repository already uses elsewhere
(`evaluation/store.py` is also SQLite with `BEGIN IMMEDIATE`). The cost is single-writer
throughput, acceptable for a coordinator that claims issues at engineering, not market, rate.

Schema-level invariants (not conventions):

- Partial unique index `lease_events(issue_id) WHERE outcome = 'ACTIVE'` — at most one owner
  per issue across every process and restart.
- Terminal states `COMPLETED`, `EXHAUSTED`, `BLOCKED` are never selected by the claim query.
- `enqueue` is idempotent and never rewrites an existing row, so replaying the eligibility
  list after a crash cannot duplicate ownership or reset the retry budget.
- `attempts` increments inside the claim transaction, so reclaiming an expired lease spends
  budget exactly once.

## What was implemented

`src/v8_next/factory/lease.py`

- `Lease` frozen dataclass (`issue_id, worker_id, token, acquired_ns, expires_ns, attempt`)
  with constructor validation and `is_expired(now_ns)` (deadline inclusive).
- `IssueState` (`PENDING | LEASED | COMPLETED | EXHAUSTED | BLOCKED`, `terminal` property),
  `LeaseOutcome` (`ACTIVE | COMPLETED | FAILED | EXPIRED | BLOCKED`), `OwnerReview` (`REQUIRED`).
- `IssueRecord` snapshot (status, attempts/budget, lease, meta, last result) and `LeaseEvent`
  attempt history row.
- `CompletionReceipt` result contract with immutable `owner_review_required=True` and
  `owner_review=REQUIRED`; constructing one that waives review raises `ValueError`, and the
  frozen dataclass rejects attribute assignment. The result mapping is read-only.
- `evidence_receipt(...)`: builds a dict from caller-supplied measurements only
  (`code_sha`, `config_sha`, `executed_tests`, `walltime_ms`, `peak_rss_kb`,
  `budget_spent`/`budget_limit`); unmeasured fields stay `None` and are labelled
  `NOT_MEASURED` in `receipt["measurement"]`. Negative or inconsistent values raise.

`src/v8_next/factory/queue.py`

- `IssueQueue(path)` with `enqueue(issue_id, meta)`, `claim(worker_id, now_ns, ttl_ns)`,
  `complete(lease, result)`, `fail(lease, reason)`, `release_expired(now_ns)`,
  `state(issue_id)`, plus `snapshot`, `history`, `block` and context-manager close.
- Deterministic dispatch order `(priority ASC, enqueue sequence ASC)`; per-issue
  `max_attempts` (default 3, overridable via `meta["max_attempts"]`), `priority` likewise.
- Claim recovers expired leases in the same transaction; `release_expired` is idempotent and
  returns only the issues recovered by that call.
- `complete`/`fail` are token-bound and idempotent for a replay of the same token; stale,
  foreign, or expired tokens raise `LeaseMismatchError`. Completion after expiry is rejected.
- Retry budget: a failed/expired attempt with the budget spent moves the issue to
  `EXHAUSTED`; no claim path ever selects it again.

`src/v8_next/factory/__init__.py` re-exports the public names for later waves.

Rationale for `EXHAUSTED` over `BLOCKED` for budget exhaustion: the acceptance text allows
either; `EXHAUSTED` names the cause (budget), while `BLOCKED` is reserved for a human
escalation via `IssueQueue.block(...)` (which refuses to overwrite a `COMPLETED` issue).

## Residual risks

- **Single-writer throughput.** Every claim takes the database write lock; measured suite
  runtime (~0.3 s for 20 tests including three concurrency tests) implies sub-millisecond
  claims, but a coordinator polling thousands of issues per second would serialise. Not
  exercised at scale.
- **Shared clock assumption.** `claim(..., now_ns, ttl_ns)` trusts the caller's nanosecond
  clock. Multiple hosts with unsynchronised clocks can expire a lease early/late; the queue
  itself never reads wall time for claims (only `time.time_ns()` for audit `updated_ns` in
  `fail`/`block`).
- **Filesystem scope.** WAL mode requires a local POSIX filesystem. SQLite on NFS/SMB is
  unsupported and not tested.
- **One connection per thread/process.** `check_same_thread=False` allows sharing but the
  connection is not a thread-safe transaction coordinator; the documented contract is one
  handle per worker (as the tests do).
- **Results are opaque JSON.** `complete` stores the caller's mapping with canonical-JSON
  validation; it does not validate that a report references real commits or tests. Evidence
  integrity is the auditor's job (F-02/F-03), not the queue's.
- **No GitHub boundary.** Eligibility, PR/branch creation and review are injected by the
  caller; this module cannot and does not prevent two coordinators from acting on the same
  issue if they use *different database files*.
