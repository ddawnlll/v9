# M4-05 — 24–48 h shadow soak, fault injection and 4 GiB resource qualification (#33)

Status: **IMPLEMENTED_WITH_EVIDENCE**. The harness and its fault matrix are implemented and
tested; the real 24–48 h wall-clock soak and the 4 GiB cgroup qualification are **NOT_RUN**
in this environment and are declared below rather than simulated.

## Objective

Run a long-lived adaptive shadow loop under bounded VPS resources, inject venue/data/process
faults deterministically, and prove from the audit trail that memory does not grow without
bound, decisions are not duplicated, and unknown-venue, missed-mark, disconnection and
protection-gap conditions stay fail-closed. No live authority may be added.

## What was implemented

`src/v8_next/factory/soak.py` (new)

- `FaultKind` — `VENUE_UNKNOWN`, `MISSED_MARK`, `DISCONNECT`, `PROTECTION_GAP`,
  `DUPLICATE_DELIVERY`, `CRASH_RESTART`, `SLOW_CONSUMER`.
- `FaultSchedule` — inclusive `[start_index, end_index]` window with a `kind` and the
  enforced `expected_invariant`. The validator refuses a schedule that declares an invariant
  weaker than the fault's default, so a caller cannot relabel `PROTECTION_GAP` as `NO_ENTER`
  to dodge the protection check. `FaultPlan` holds the windows plus `max_backlog`, exposes
  `active_at`/`kinds_at`, and has a content `digest()` (`canonical_digest` over the canonical
  JSON) so identical plans reproduce identical identities. `default_plan(iterations)` lays
  disjoint contiguous windows deterministically — no RNG anywhere.
- Invariant map (one per fault, enforced by the runner):
  | Fault | Invariant | What must not happen |
  |---|---|---|
  | `VENUE_UNKNOWN` | `NO_ENTER` | ENTER while venue state is unknown |
  | `MISSED_MARK` | `NO_ENTER` | ENTER without a fresh mark |
  | `DISCONNECT` | `NO_NEW_RISK` | ENTER while the link is down (EXIT/HOLD allowed) |
  | `PROTECTION_GAP` | `NO_PROTECTED` | a `PROTECTED` claim while protection is missing |
  | `DUPLICATE_DELIVERY` | `NO_DUPLICATE_DECISION` | the same decision id emitted twice |
  | `CRASH_RESTART` | `RECOVERED_STATE` | restart iteration not reporting recovered state |
  | `SLOW_CONSUMER` | `BOUNDED_BACKLOG` | backlog above the ceiling, or unmeasured backlog |

  `DecisionObservation.live_authority=True` is additionally a `NO_LIVE_AUTHORITY` violation
  regardless of the active window; this harness cannot confer authority.
- `SoakRunner` drives a caller-supplied `step(context)` for at most `iterations` steps or
  `duration_target_s` wall seconds (production shadow wiring deliberately out of scope).
  `StepContext` exposes the index, active faults, restart flag, generation and a read-only
  `DecisionJournal` (durable decision ids). A `SimulatedCrash` from the step is retried once
  at the same index with `restart=True` and the journal intact; a second crash propagates.
  Duplicate ids are counted against the durable journal, not against per-session memory, so a
  restart cannot hide a re-emit.
- Sampling every `sample_every` iterations (and at index 0 and the final index): RSS, CPU
  (`time.process_time`), throughput, swap and disk free bytes. `None` is preserved for every
  unmeasurable value; it is never coerced to zero.
- RSS growth: least-squares slope over sample indices; flagged when the slope exceeds
  `DEFAULT_RSS_GROWTH_LIMIT_BYTES_PER_SAMPLE` (64 KiB/sample) with at least
  `MIN_GROWTH_SAMPLES` (5) RSS samples. The threshold and slope both appear in the report.
- `SoakReport` (frozen) — iterations, elapsed/target/actual duration, samples, peak/median
  RSS, slope, duplicates, invariant violations, crash restarts, live-authority attempts,
  throughput, `declared_hardware_profile`, `rss_source`, `soak_status` and `fail_closed`.
  Validators re-derive `soak_status`, `memory_growth_detected` and `fail_closed`, so a
  hand-built report cannot claim `COMPLETE` for a short run or hide a leak.
  `fail_closed` is true only when there are no invariant violations, no duplicate ids and no
  measured unbounded RSS growth.
- `--duration` CLI plus `--iterations` safety cap, `--sample-every` and `--out`. It runs a
  no-op shadow step and prints the frozen JSON report; a genuine 24–48 h shadow loop is not
  wired, so the CLI normally reports `SHORT_RUN`.

## Test evidence

`tests/test_soak_fault_injection.py` — 17 passed (`pytest -q tests/test_soak_fault_injection.py`).
The fault matrix is asserted per fault (specific invariant + fault attribution, not "no
crash"): venue-unknown/missed-mark `NO_ENTER`, disconnect `NO_NEW_RISK` with EXIT still
allowed, protection-gap `NO_PROTECTED`, duplicate delivery both deduped (zero duplicate ids)
and flagged when re-emitted, crash/restart `RECOVERED_STATE` plus a `SimulatedCrash` mid-loop
that loses transient state and recovers 8/8 decisions with zero duplicates, and slow-consumer
backlog overflow plus unmeasured backlog. RSS tests inject samplers: +100 KiB/sample is
flagged (slope ≈ 100 000) and a constant loop is not (slope 0.0). A short run is `SHORT_RUN`
with `duration_actual_s < duration_target_s`, and re-labelling it `COMPLETE` fails pydantic
validation. Footer: ruff clean, `mypy` strict clean on the module and test.

Harness smoke run (not a soak), measured on this host:

```
PYTHONPATH=src python -m v8_next.factory.soak --duration 3600 --iterations 200 --sample-every 40
iterations=200  duration_actual_s=0.00107  duration_target_s=3600
soak_status=SHORT_RUN  fail_closed=true  duplicates=0
peak_rss_bytes=61,358,080  median_rss_bytes=61,349,888
rss_growth_slope_bytes_per_sample=105.8  memory_growth_detected=false
rss_source=resource.getrusage ru_maxrss (peak high-water on macOS)

```

## Declared environment (measured 2026-11-05)

- Host: macOS 26.1, arm64, 19,327,352,832 B RAM (18 GiB), 11 CPUs, ~76.6 GB free on `/`.
- Product target: 4 GiB RSS / 2 vCPU VPS. This host is **not** a 4 GiB cgroup.

## NOT_RUN / UNSUPPORTED / BLOCKED

| Claim | Status | Missing prerequisite |
|---|---|---|
| Real 24–48 h wall-clock shadow soak | **NOT_RUN** | No production shadow loop is wired, and a multi-hour wall-clock window is not available in this session. The harness and fault matrix are runnable; the duration claim is not. |
| 4 GiB cgroup OOM/swap-headroom qualification | **UNSUPPORTED** | Host has 18 GiB and no 4 GiB cgroup. `declared_hardware_profile` declares the target; nothing in this run measured it. |
| Swap growth under pressure | **NOT_MEASURED** | Swap sampler reads `/proc/meminfo` (Linux only); on the macOS host every sample is `null`, not zero. |
| Venue/data faults against a live venue | **NOT_RUN** | No live credentials or venue connection are used by design; faults are injected synthetically. |
| Peak RSS on macOS | **UNSUPPORTED as current-RSS** | `ru_maxrss` is a high-water mark; the report records `rss_source` so a slope from this source cannot be read as current-RSS behaviour. |

## Fail-closed and authority notes

- No live orders, credentials, sealed-OOS reads or `main` writes were introduced.
- `live_authority=True` on an emitted decision is recorded and fails `fail_closed`; no code
  path grants or propagates authority.
- Duplicate detection is journal-based and survives simulated process death; duplicate ids
  always fail `fail_closed` even outside a `DUPLICATE_DELIVERY` window.
- A report whose `soak_status` disagrees with `duration_actual_s`/`duration_target_s` cannot
  be constructed, so a short harness run cannot be promoted to a completed soak by editing
  one field.

## Known risks

- Real-loop behaviour (strategy state, belief evolution, consumer backpressure) is not
  exercised: the caller-supplied step is synthetic in tests and a no-op in the CLI.
- On Linux the RSS sampler is current RSS from `/proc/self/statm`; on macOS it is peak RSS,
  so a genuine 24–48 h qualification must run in the 4 GiB Linux target to be meaningful.
- The 64 KiB/sample growth ceiling is a declared engineering threshold, not a statistical
  test; sampling cadence changes the bytes-per-sample scale and must be recorded with the
  report (it is: `rss_growth_limit_bytes_per_sample` plus the sample indices).
