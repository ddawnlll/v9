**Status: implementation COMPLETE, measurement PARTIAL — director certifies.**
`implementation_status`: measured on 1 leg / 2.96 months (BTCUSDT 1h, 2025 Q1). The
40-leg / 12-month scope is **NOT_RUN**. Order/fill/report parity streams are **NOT_RUN**
(no economic execution replay in this slice), so the parity gate returns **BLOCKED**, not PASS.
**The 4 GiB target is NOT certified** — only an arithmetic comparison of the measured peak RSS
against 4 GiB is published, because the run did not execute inside a 4 GiB cgroup.

## 1. Objective

Produce a resource baseline the project can cite instead of asserting: a machine-readable receipt
with cold/warm wall, median/p95 over ≥5 repetitions, peak RSS from `resource.getrusage`, runtime
versions, code SHA, config SHA and tape identity; eliminate measured full-prefix and 28× indicator
recomputation; and gate a candidate against the baseline on decision digests, fail-closed.

PR #1's 2-vCPU / 4-GiB container figures (`reports/performance/PERFORMANCE_REPORT.md`) are treated
as a **proposed** baseline subject to review. Its harness was **not re-run**. Every number below
comes from this slice's own harness and receipt.

## 2. Implementation

`src/v8_next/evaluation/resource_baseline.py` (new, 1156 lines):

* `TimingSummary` / `MemorySummary`: a quantity is either `MEASURED` with its numbers, or
  `NOT_MEASURED` / `NOT_RUN` with a named refusal. A model validator rejects numbers under a
  non-measured status, and rejects an empty field without a refusal reason.
* `measure(operation, warmup, repetitions)`: first invocation measured as the **cold** sample, then
  a discarded warmup, then ≥5 warm samples; median / nearest-rank p95 / min / max from
  `time.perf_counter`; peak RSS from `resource.getrusage(RUSAGE_SELF)` with the platform's real unit
  (`bytes` on macOS, `kibibytes` on Linux) published alongside the raw value.
* `TapeIdentity`, `ScopeCoverage`, `runtime_identity()`, `git_sha()`, `config_sha256()`: the receipt
  binds numbers to the exact tape (SHA-256 + bytes + bars), runtime (Python/NautilusTrader/Polars/
  numpy/pydantic), code SHA, and a digest of the effective workload configuration. Anything
  unobtainable is a refusal string, never a placeholder.
* `parity_gate(baseline, candidate)`: five streams (`decision`, `order`, `fill`, `funding`,
  `report`). Precedence is fail-closed — observed drift is `FAIL`; otherwise a missing digest on
  either side is `BLOCKED`; only five matching digests are `PASS`.
* Two measured workloads: `replay_expert_decisions` (per-bar `observe_all_28`, both the baseline and
  the `FeatureCache` candidate path) and `replay_feature_values` (the five shared indicator specs
  read by two consumers per bar).

No change was needed in `src/v8_next/domain/market.py`: the existing `_prefix_df` identity plus
`extend_causal_frame` already provide the incremental primitive the cache and engine rely on, and
existing public signatures are untouched.

### 3.1 Measured resource result (code SHA `e0871451c949ce563487d9e0b8072b30f30176c3`)

Workload: 28-expert ensemble, 2,160 bars, 60,480 stances.

| Mode | Cold wall | Warm median | Warm p95 | Warm min / max | Peak RSS | OOM |
|---|---|---|---|---|---|---|
| baseline (`observe_all_28`, no cache) | 0.8651 s | 0.8765 s | 0.8872 s | 0.8430 / 0.8872 s | 226,344,960 B = **215.9 MiB** | False |
| candidate (`FeatureCache` engine) | 0.6464 s | **0.6559 s** | 0.6708 s | 0.6278 / 0.6708 s | 230,752,256 B = **220.1 MiB** | False |

Warm median speedup **1.34×**; peak RSS +4.2 MiB (+1.9 %; the retained incremental state).
Peak RSS is 5.4 % of the 4 GiB target on this 1-leg/3-month slice — **within the target for the
measured scope only**; the 40-leg/12-month scope is NOT_RUN and is not extrapolated here.

Repetitions are 5 warm samples after one discarded warmup plus the cold sample; the p95 is the
nearest-rank 5th of 5 samples and is therefore equal to the maximum, which the receipt reports as
such rather than as a stable tail.

### 3.2 Elimination of full-prefix / 28× recomputation (component evidence)

The candidate path retains the incremental `FeatureEngine` prefix instead of recomputing:

* cache stats over the real tape: `extensions = 2159`, `reseeds = 0`, `invalidations = 0`,
  `bars_observed = 2160` — the prefix was proved append-only on every bar, so no history was
  re-read and no indicator was recomputed from ``[0, n)``.
* feature-read workload (2 consumers × 5 specs × 2,121 eligible bars = 21,210 reads): direct
  full-prefix kernels `cold 4.5540 s / warm median 4.5845 s / p95 4.6537 s`, RSS 170.1 MiB;
  `FeatureCache` `cold 0.8113 s / warm median 0.7995 s / p95 0.8048 s`, RSS 185.5 MiB —
  **5.73× faster** on the same values digest. Command:

```

  --tape research/tape/btcusdt-1h-2025Q1 --workload features --mode {baseline,candidate} \
  --consumers 2 --repetitions 5 \
  --out reports/overnight/evidence/receipts/M1-06-features-{baseline,candidate}-receipt.json
```

(Full M1-06 detail, including invalidation and bound counters, is in `M1-06.md`.)

### 3.3 Parity gate result — **BLOCKED**

`decision` PASS (`8ecef5f05713f19e…` both sides over all 60,480 stances), `funding` PASS
(`20788c118a0b0e64…`, digest of the tape's funding events), `order` / `fill` / `report` BLOCKED with
`DIGEST_MISSING:<stream>:baseline+candidate`. Three unrun streams cannot certify the candidate, so
the gate reports **BLOCKED** — this is the fail-closed behaviour, not a pass.

Why the execution streams are absent: the cache lives at the expert-decision layer; this slice runs
no Nautilus economic replay, and `adapters/expert_strategy.py` is outside this worker's ownership,
so wiring the cache into a full execution replay is out of scope. Labelling them NOT_RUN is the
honest record; fabricating an order digest would be a fabricated claim.
