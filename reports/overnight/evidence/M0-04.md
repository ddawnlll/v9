**Issue:** #5 · **Worker:** `DurableIntent` · **Branch:** `wave3/w3g`

## Objective

Record economic intents durably before they reach the venue, survive a crash at any
point between journal write, native submission and callback observation, and make
duplicate delivery harmless — without introducing a second execution authority. The
native Nautilus OMS remains the only thing that submits orders; this module only
journals intent identity, attempts and observed evidence.

## What was implemented

`src/v8_next/adapters/durable_intent.py`:

- **Identity** — `derive_intent_identity(decision_id, instrument_id, side, quantity,
  price, policy_version) -> IntentIdentity`. `intent_id` is a domain-separated
  `canonical_digest` (`v8-next.durable-intent.v1`) over canonicalised decimals
  (`1.0` and `1.00` are the same intent). `client_order_id` is `v9i-` plus the first
  32 hex chars of the digest (36 chars, 128-bit identity), derived identically in
  every process; no clock, pid or random source participates.
- **Record** — frozen `IntentRecord` with the identity inputs, `state`, `attempt`,
  `created_ns`/`updated_ns`/`submitted_ns`/`acknowledged_ns`/`terminal_ns`,
  `venue_status`, `filled_qty` and `reconcile_note`. `__post_init__` enforces the
  state invariants (e.g. `FILLED` exactly carries `filled_qty == quantity`;
  `REJECTED` carries no fill; terminal states carry `terminal_ns`; `UNKNOWN` is never
  terminal).
- **State machine** — `IntentState` is exactly `PENDING | SUBMITTING | SUBMITTED |
  ACKNOWLEDGED | PARTIALLY_FILLED | FILLED | CANCEL_PENDING | CANCELED | REJECTED |
  UNKNOWN`.
- **Outbox** — SQLite (`journal_mode=WAL`, `synchronous=FULL`, `busy_timeout`) with two
  tables: `intents` (`client_order_id` UNIQUE) and `intent_fills`
  (`PRIMARY KEY(client_order_id, cumulative_qty)`). Every mutating method runs inside
  `BEGIN IMMEDIATE` and persists with a conditional update keyed on the previous
  `(state, attempt)`; `rowcount != 1` refuses with `CONCURRENT_TRANSITION`.
  - `record_intent` — idempotent for identical content; a colliding client order id is
    refused (`IDENTITY_COLLISION`).
  - `begin_submit` — `PENDING → SUBMITTING` (attempt + 1, `submitted_ns`), and nothing
    else. Any other state raises `DuplicateSubmit` (including `UNKNOWN`).
  - `observe_ack` — `SUBMITTED → SUBMITTED`, `ACCEPTED → ACKNOWLEDGED`, `REJECTED →
    REJECTED` only with zero fill evidence, `UNKNOWN → UNKNOWN` (never terminal).
    `FILLED`/`PARTIALLY_FILLED` without matching cumulative evidence and `CANCELED`
    routing raise/route through the explicit paths; duplicates are byte-identical
    no-ops (no write, `updated_ns` unchanged).
  - `observe_fill` — cumulative, monotonic; same cumulative quantity is a no-op with
    one fill row, a lower reading never regresses evidence, anything above the ordered
    quantity raises `OverfillError` before any write.
  - `request_cancel` — `CANCEL_PENDING`; refused while `PENDING` (nothing exists) or
    `UNKNOWN` (existence unproven); terminal records are untouched.
  - `observe_cancel` — terminal `CANCELED`; a completed fill is never downgraded and a
    cancel ack after a fill is a no-op.
  - `recover(now_ns)` — returns every record whose venue outcome is unproven and marks
    `SUBMITTING` (submit call unobserved), `SUBMITTED` (ack unobserved) and
    `CANCEL_PENDING` (cancel outcome unobserved) as `UNKNOWN` with the matching
    `RECOVERED_*` note. `PENDING` stays `PENDING`, so a submit after a pre-submit crash
    is safe and reuses the same client order id. Already-`UNKNOWN` records are returned
    again (stable order), never guessed.
  - `reconcile(record, venue_view, now_ns)` — evidence-only resolution of `UNKNOWN`
    from injected `VenueView(orders, fills)`. Client id missing from both stays
    `UNKNOWN` forever. Multiple conflicting statuses, `REJECTED` with fills,
    `FILLED` below the ordered quantity, `PARTIALLY_FILLED` with zero quantity and
    cumulative overfill raise typed errors and write nothing.
- **Typed failures** — `OutboxError` base with stable `code` plus `InvalidTransition`,
  `DuplicateSubmit`, `OverfillError`, `VenueEvidenceError`, `UnknownIntent`. An unlisted
  venue status string is a `VenueEvidenceError`; it is never coerced to `UNKNOWN`.

No order construction, submission call, credential or second ledger exists in the
module. The caller journals `begin_submit`, calls the native OMS, then feeds native
callbacks into `observe_ack`/`observe_fill`/`observe_cancel`.

## Residual risks and limits

- The journal is deliberately not an execution authority. It cannot detect a native
  submit that bypassed `begin_submit`; callers must journal the attempt before calling
  the OMS. Reuse of the native OMS is unchanged.
- `recover` marks only unobserved-outcome states (`SUBMITTING`, `SUBMITTED`,
  `CANCEL_PENDING`) and existing `UNKNOWN` rows as `UNKNOWN`. Known-live
  `ACKNOWLEDGED`/`PARTIALLY_FILLED` orders keep their fill evidence; the native OMS cache
  remains responsible for live-order catch-up. A stricter policy can be layered by
  reconciling those rows explicitly, but that is not required by this issue and would
  block cancellation of known-live orders.
- MISSING venue evidence leaves an `UNKNOWN` record stuck forever, by contract. An
  operator must inject venue truth (or a later explicit cancel/reject event) to resolve
  it; absence is never read as terminal.
- A crash between the committed `SUBMITTING` write and the native submit call is
  indistinguishable from a crash after the native call, so it also becomes `UNKNOWN`
  and stays fail-closed until reconciled. This is the conservative choice.
- The module is single-process oriented (SQLite WAL); a shared network filesystem was
  not exercised. Two local connections/handles are serialized by `BEGIN IMMEDIATE` and
  the conditional update.
- `NOT_RUN`: no live venue, no Nautilus submission, no integration wiring into
  `expert_strategy.py` (not in this issue's scope). Nothing was pushed or merged.
