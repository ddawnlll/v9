# F-02 — Bounded Pi issue-to-PR worker without production authority (#36)

Status: **IMPLEMENTED_WITH_EVIDENCE** (integration and final issue closure remain the director's call).

## Objective

One assigned issue must be able to travel `issue -> isolated branch -> minimal code/test/audit
-> draft PR or typed BLOCKED receipt` with no human in the loop *and* no production authority:
no live credentials, no sealed OOS access, no auto-merge to main, no deploy. Every run must
record its logs, base/head SHA, costs and review requirement, and a deliberate failure must
produce `BLOCKED` rather than a partial publish.

## Design

**Pluggable four-phase pipeline.** `BoundedWorker` owns the *sequence and the gates*; the
effects live behind a `WorkerStep` protocol with one step per phase
(`prepare`, `implement`, `verify`, `publish`). Tests inject fakes; a real deployment injects
git/pytest/`gh` tooling. The worker never shells out itself, so it cannot accidentally hold a
credential or reach a venue.

**Explicit budget, checked before every phase.** `TaskBudget(max_tokens, max_wall_s,
max_rss_kb, max_cpu_s, max_attempts)` and each `StepResult` must report what it consumed
(`tokens`, `wall_ms`, `cpu_ms`, `peak_rss_kb` are required fields, not defaults). Totals are
accumulated and compared to the ceilings *at the top of each phase*, so an over-budget run
cannot reach `publish`. `TaskBudget.max_attempts` is mirrored into the queue's retry budget by
`BoundedWorker.register`.

**Authorization is a closed set, not a policy string.** `Capability` enumerates
`REPO_READ`, `BRANCH_WRITE`, `TEST_EXECUTION`, `DRAFT_PR_CREATE` (allowed) and
`MAIN_MERGE`, `PUSH_TO_MAIN`, `SEALED_OOS_ACCESS`, `LIVE_CREDENTIALS`, `DEPLOY`
(`FORBIDDEN_CAPABILITIES`). A step is checked twice — on its *declared* `requests` before it
runs and on the `requests` it *returns* afterwards — and a refusal raises
`WorkerAuthorizationError` (with `.capability`, `.phase`, `.reason`) while the issue is already
durably `BLOCKED` and its outcome recorded, so refusing does not lose the audit trail.
`prepare` naming `main`/`master` is refused as `PROTECTED_BRANCH:<name>` with capability
`PUSH_TO_MAIN`, and `StepResult` itself rejects a non-draft publish (`draft is not True`), so a
step cannot even construct an "open PR, auto-merge" result.

**Terminal states are typed and exhaustive.** `PUBLISHED_DRAFT` (all four phases ok, inside
budget, draft PR recorded), `BLOCKED` (missing step, step raised, phase mismatch, failed
verify, forbidden capability, protected branch — failure text preserved, no PR state),
`EXHAUSTED` (tokens/wall/CPU/RSS/attempts). The durable transition happens before the receipt
is returned: `complete` for a publish, `IssueQueue.block` for a block, `IssueQueue.fail` for
exhaustion (which lands on `EXHAUSTED` when the attempt budget is spent, `PENDING` when a retry
remains). Owner review is pinned: `owner_review_required=True`,
`owner_review=OwnerReview.REQUIRED`.

**Receipt.** `WorkerReceipt` carries `base_sha`, `head_sha`, `code_sha`, `config_sha`
(= `TaskBudget.digest`, a canonical digest of the ceilings), `executed_tests`, `commands`
(the log), `walltime_ms`, `cpu_ms`, `peak_rss_kb`, `budget` plus `budget_use` (used / limit /
within per dimension), `budget_violation`, `failure`, per-phase results, `durable_state`,
`retry_allowed`, `owner_review`, a canonical `digest`, and `measurement()` marking unmeasured
fields `NOT_MEASURED`. `to_result()` is what `IssueQueue.complete` stores, so the durable result
and the in-memory receipt cannot disagree.

## Residual risks

- **The step implementations are not in this module.** F-02 proves the *driver* contract; the
  git/pytest/`gh` steps (and therefore real branch/PR creation) are injected and were exercised
  only with fakes. A real step could still hold a credential internally — the guard checks what
  a step *declares and returns*, not what an opaque callable does.
- **Costs are self-reported.** `StepResult` costs are trusted inputs; the worker does not
  measure a subprocess's RSS or CPU itself. A lying step defeats the budget. Production steps
  must derive the numbers from `resource.getrusage`/token counters, which is the caller's job.
- **Residual publication on overspend.** The budget is checked *before* each phase, so a run
  cannot *reach* publish over budget. A publish step whose own cost pushes the total over the
  ceiling cannot be un-published: the run is reported `EXHAUSTED` (never `PUBLISHED_DRAFT`) but
  `draft_pr_url` is still recorded, because the PR exists. The receipt is honest about both.
- **EXHAUSTED may leave the queue `PENDING`.** If the attempt budget still has room, a
  token/wall/CPU/RSS blow-out calls `IssueQueue.fail`, which returns `PENDING`; the run is
  `EXHAUSTED` with `retry_allowed=True`. The tests assert durable `EXHAUSTED` with
  `max_attempts=1`. A coordinator that wants one blow-out to be terminal for the issue should
  register with `max_attempts` equal to the budget.
- **Lease TTL vs wall budget.** A run whose `TaskBudget.max_wall_s` exceeds `lease_ttl_ns` can
  have its lease expire mid-run; the terminal `complete`/`block`/`fail` then raises
  `LeaseMismatchError` (fail closed, nothing recorded twice). No automatic renewal exists.
- **No sandbox.** The worker does not confine a step's filesystem/network access; it only
  refuses declared capabilities. Branch isolation is the prepare step's responsibility.
- **Memory write ordering.** The durable queue transition is committed before the memory row;
  a crash between the two loses the memory outcome (not the durable state). Replaying the same
  run re-records it idempotently only if the attempt/outcome content matches.
